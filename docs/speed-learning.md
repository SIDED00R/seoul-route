# 안내 궤적과 사용자별 속도 학습 (이슈 #32, 2026-09-13)

계획 v2 의 Phase 2b(안내·foreground 위치 스트림·배치 업로드)와 Phase 3(속도 학습)을 한 기능으로 붙였다.
목표: 사용자가 실제로 걷고 따릉이를 탄 속도로 예상시간을 내는 것. 표본이 없으면 사전값(걷기 1.2·자전거 3.5 m/s)이다.

## 흐름

```
앱 상세 화면 "안내 시작"
 → POST /trips (trip id 발급)
 → 5초마다 위치(geolocator, 위치 포그라운드 서비스 — 화면이 꺼지거나 다른 앱으로 가도 이어진다, 이슈 #60) → 현재 구간 수단(walk/bicycle/transit) 태그
 → 20개(≈100초) 또는 30초마다 POST /trips/{id}/traces (실패분은 다음 배치 앞에 붙여 재전송, 요청당 최대 1000개, 서버는 (trip, ts) 중복 무시)
 → "안내 종료": 남은 샘플 flush(줄어드는 동안 반복, 실패하면 남긴 채 중단·재시도 안내) → POST /trips/{id}/end (409 면 이미 닫힌 것으로 보고 완료 처리)
    → 서버: 수단별 이동 중 중앙값(speed.TripSpeeds) → speed_profiles 수축 갱신 → 결과 대화상자
 → 다음 POST /routes/plan 부터 OTP walk/bicycle speed 에 내 속도가 들어간다
```

앱 `lib/guide/leg_tracker.dart` 가 현재 구간을 정한다: 위치가 현재 구간 끝점 40m 안에 들어오거나, 다음 구간 경로선 위 25m 안에서
그 경로선을 40m 이상 따라가면(정확도 50m 이하로 연속 2회) 다음 구간으로 넘긴다. 손으로 앞뒤 이동도 된다.
위치는 2초 간격으로 받고 서버에는 5초 간격으로 솎아 올린다(`trace_uploader.dart` 의 minGap) — 아래 표본 수 기준이 5초 간격을 전제한다.
샘플의 mode 는 그 시점 구간의 수단이다(WALK→walk, BICYCLE→bicycle, 탑승 구간→transit). transit 샘플은 저장만 하고 학습에 쓰지 않는다.

## 속도 산출 (`backend/internal/speed`)

| 단계 | 규칙 | 근거(초기값, 실기기 궤적으로 재보정) |
|---|---|---|
| 표본 필터 | accuracy ≤ 30m | 도심 GPS 반사 표본 제거 |
| 연속 쌍 | 같은 수단, 간격 2~30초 | 앱 5초 간격. 30초 넘게 비면 구간 속도가 아니다 |
| 속도 상한 | 걷기 3.0 · 자전거 12.0 m/s | 그 이상은 GPS 점프 |
| 이동 중 | 걷기 ≥ 0.3 · 자전거 ≥ 0.5 m/s | 정지(횡단보도 대기)는 Phase 4 가 맡으므로 뺀다 → OTP speed(이동 속도)와 같은 의미 |
| 활동 불일치 | 샘플 `activity`(폰 활동 인식)가 walk/bicycle/vehicle 이면서 구간 수단과 다르면 그 쌍 제외, `mismatch` 로 집계 | 구간 끝점에 안 가고 다른 역에서 타면 차량 안 샘플이 walk 로 찍힌다(이슈 #42). still/unknown/없음은 판단 안 함 |
| trip 값 | 이동 중 쌍의 중앙값, 쌍 12개(1분) 미만이면 미반영 | robust median |
| 프로파일 | `(n0·μ0 + Σ v_trip) / (n0 + n)`, n0 = 5 | 첫 trip 이 1/6 만 움직인다. `speed_profiles.sum_speed_mps` 가 Σ |

OTP 의 bicycle speed 는 평지 이동 속도 정의라 GPS 이동 중 중앙값과 의미가 맞는다(계획 v2 의 "관측/예측 비율 보정 계수"는 두지 않았다 — 실기기 자료가 쌓이면 판단).

## 개인정보

- 궤적은 서버가 발급한 trip id 로만 받고, 원본은 30일 뒤 지운다(`speed.PurgeOldTraces`, api 기동 후 1시간마다, 샘플 `ts` 기준. 그래서 서버 시각보다 5분 넘게 미래인 `ts` 는 업로드에서 400). trip 별 속도와 프로파일만 남는다.
- 탈퇴(`DELETE /users/me`)는 trip 을 지우고 traces 는 `ON DELETE CASCADE` 로 같이 사라진다(테스트로 확인).
- 앱은 백그라운드 위치 권한("항상 허용")을 요구하지 않는다(`ACCESS_FINE_LOCATION`/`COARSE` 만). 안내를 시작하면 위치 포그라운드
  서비스(`FOREGROUND_SERVICE_LOCATION`, 알림 "안내 중")를 올려 화면이 꺼지거나 다른 앱으로 가도 수집한다(이슈 #60). 서비스를 안내
  화면에서 시작하므로 "앱 사용 중에만 허용" 권한으로 된다. 알림 권한(`POST_NOTIFICATIONS`)은 안내 시작 때 묻는다.
- 활동 인식(`ACTIVITY_RECOGNITION`, 이슈 #42): 안내 화면에서만 `flutter_activity_recognition` 스트림을 받아
  `guide/activity_classifier.dart` 가 끈적하게 판정한다. 플러그인은 판정이 **바뀔 때만** 이벤트를 주므로(같은 판정이
  이어지는 동안은 무이벤트 — 플러그인 소스와 AOSP SharedPreferences 리스너 동작으로 확인) 횟수가 아니라 시간으로 확정한다:
  새 판정을 후보로 두고 위치 샘플(5초)마다 후보가 20초 이상 유지됐으면 현재 활동으로 삼는다. LOW 신뢰도·UNKNOWN·STILL 은
  후보가 되지도, 후보를 지우지도 않는다(신호 대기로 차량↔정지가 번갈아 와도 차량 후보가 살아남는다).
  샘플 `activity` 로 올라가고 서버는 원본 궤적과 함께 30일 뒤 지운다. 권한을 거부하면 안내는 그대로 되고 `activity` 만 빠진다.
  화면은 "활동 걷기/자전거/차량/미상" 을 보여 주고, 구간 수단과 어긋나면(도보 구간에 차량 등) 빨간 안내를 띄운다 —
  대중교통 구간의 걷기(역 구내)는 정상으로 본다. 실기기(S23 울트라) 확인: 안내 시작 후 걷기 시작 → 약 35초 뒤 "활동 걷기",
  서버 샘플 `activity` 도 `unknown` → `walk`(`docs/app/18-activity-walk.png`).

## 실기기 첫 검증 (2026-09-15, 갤럭시 S23 울트라 · Android 16 · 이슈 #36)

- 연결: USB 디버깅 + `adb reverse tcp:8081 tcp:8081` → 앱 서버 주소 `http://127.0.0.1:8081`(Compose 가 loopback 에만 열려 있어 Wi-Fi 로는 못 붙는다). 설정 "연결 확인" → `서버 OK · 내 속도 — 걷기 1.27 m/s (trip 1회)`(전날 에뮬레이터 학습값이 그대로 보인다).
- 역삼역→선릉역 도보 22분(학습 속도 반영), 상세 지도 타일 정상, "안내 시작" → 위치 권한 → 실제 GPS: `샘플 5 · 정확도 23m · 업로드 4 · 대기 1`, 끝까지 17,044m(집에서 실행). 실내라 30초 뒤 종료: `걷기 0.73 m/s (3쌍, 표본 부족·미반영)` — 쌍 12개 미만 게이트가 실내 GPS 흔들림을 걸러 프로파일이 1.27 그대로다.
- 실기기에서만 난 문제: 하단 패널이 시스템 내비게이션 바에 가려졌다(`docs/app/12-phone-guide-cutoff.png`) → `SafeArea(top: false)` 로 감쌈(`13-phone-guide-safe-area.png`).
- 아직 안 한 것: 실제로 걸으며 속도 상수 재보정. 집 밖에서는 PC 서버에 닿을 길이 필요하다(Tailscale 등) — 그전에는 USB 를 꽂은 채 실내에서만 된다.

| trip 발급 실패 | API 컨테이너를 멈추고 안내 시작 → 10초 제한 뒤 화면 `trip 발급 실패: TimeoutException …`, logcat `position updates stopped` → `Stop service in foreground`, 포그라운드 서비스 해제 |

측정은 실내 샘플이 걷기 속도에 섞이지 않게 대중교통 구간(2/3)으로 넘긴 뒤 했다(transit 샘플은 학습에 쓰지 않는다).

## 알려진 한계

- 위치 포그라운드 서비스는 앱 프로세스 안에서 돈다. 앱 프로세스가 죽으면 수집도 멈추고, 30초 넘게 비면 그 구간은 학습에서 빠진다.
- 구간 자동 넘김은 끝점 40m 반경과 다음 구간 경로선 인계 둘뿐이다. 경로를 벗어나도 재탐색하지 않는다. 활동 인식은 불일치 샘플을 학습에서 빼고
  화면에 알릴 뿐 구간을 자동으로 넘기지는 않는다(유지 20초·LOW 무시는 초기값, 실기기 궤적으로 재보정). 활동 라벨은 판정
  전환보다 20초 이상(위치 샘플 간격 탓에 25초쯤까지) 늦게 바뀐다. `mismatch` 는 간격 게이트(2~30초)를 통과한 쌍 중 불일치로 뺀 수라 정지 중이던 쌍도 포함한다.
- 실기기 궤적으로 상수(정확도 30m·이동 중 임계·반경 40m·경로선 인계 25/40/60m)를 재보정하지 않았다.
- 활동 인식 원시 판정(`traces.activity_raw`·`activity_conf`)은 2026-09-18 부터 함께 저장한다. 판정이 안 온 것과 직전 값이
  유지된 것을 구분하려는 진단용이고 속도 계산에는 쓰지 않는다.
- 대중교통 leg 안의 걷기(환승 통로)는 transit 으로 태그돼 학습에 안 들어간다.
- 안내 중 뒤로가기(시스템 제스처·앱바 화살표)는 바로 나가지 않고 "안내를 종료할까요?" 를 묻는다(`guide/end_confirm.dart`, 이슈 #46).
  "종료" 는 안내 종료 버튼과 같은 흐름(샘플 전송·속도 반영), "계속 안내"·바깥 탭은 화면에 머문다. trip 발급 전(위치 권한 거부 등)에는
  그냥 나간다. 앱을 강제 종료하면 그 안내는 종료 없이 남는다(대기 샘플 유실, 서버 trip 은 `ended_at` 없이 남지만 30일 뒤 궤적
  삭제·탈퇴 시 삭제는 그대로).
