# 안내 화면 내비게이션 (이슈 #67, 2026-09-18)

안내 화면이 궤적만 모으던 것을 "지금 뭘 해야 하는지" 보여 주고 읽어 주는 화면으로 바꿨다. 위치 반영 주기와 구간 넘김
판정도 같이 손봤다.

## 서버가 내려주는 것 (`backend/internal/otp/client.go`)

OTP `planConnection` 쿼리에 세 가지를 더했다.

| 필드 | 내용 | 비고 |
|---|---|---|
| `legs[].steps[]` | `dir`(OTP relativeDirection)·`abs`·`street`·`distance_m`·`lat`·`lon`·`exit`·`entrance` | 도보·자전거 구간. `entrance` 는 `feature { ... on Entrance { name } }` 로 받은 역 출입구 이름("서울 2번 출구") |
| `legs[].stops[]` | 중간 정차 `name`·`lat`·`lon`·`stop_id`·`offset_sec` | `offset_sec` 은 구간 출발 기준 상대초라 실시간 보정이 시각을 옮겨도 그대로 쓴다 |
| `legs[].headsign` | 차량 행선지("사당"·"성수") | 방면 표시·발화에 쓴다 |

- `street` 는 OTP `bogusName` 이 true 인 생성 이름(path·sidewalk·pathway)을 버린 값이다. 실측에서 서울역 주변 도보
  단계 7개 중 4개가 그런 이름이었다.
- 기존 `intermediateStops { name }` 는 `intermediatePlaces` 로 대체했다. `next_stop`(방면 판별) 은 그대로 첫 중간 정차
  이름이다.
- `feature` 는 union 이라 inline fragment 없이 요청하면 plan 전체가 스키마 오류로 실패한다.

## 앱

- **위치 2초, 업로드 5초**: 위치 스트림 `intervalDuration` 을 2초로 줄이고, `TraceUploader.minGap` 5초로 솎아 서버에
  올린다. 서버 속도 학습의 표본 수 기준(`speed.MinPairs` 12 = 5초 1분치)이 5초 간격을 전제한다.
- **구간 넘김**(`lib/guide/leg_tracker.dart`): 기존 "끝점 40m" 에 더해, 뒤 구간 경로선 25m 안에서 그 경로선을 40m 이상
  따라갔고(정확도 50m 이하) 연속 2회 맞으면 그 구간으로 넘긴다. 바로 다음 구간은 수단을 가리지 않는다. 그보다 뒤는
  현재 구간이 대중교통·역 안 환승 통로일 때만, 지상 구간(도보·자전거)에 한해 본다 — 지상 도보 중에 멀리 있는 뒤
  구간으로 건너뛰지 않게. 지상 구간끼리는 현재 경로선에서 60m 이상 벗어났을 때만 넘긴다(나란한 길 오판 방지).
- **지하 구간**(이슈 #73): 지하에서는 위 두 판정이 모두 서지 않는다 — 2026-09-18 실기기 궤적에서 지하철 표본 231개 중
  92개가 정확도 50m 밖이었고 안내는 31분 넘게 첫 열차 구간에 머물렀다. 그래서 대중교통·역 안 환승 통로(`in_station`)
  구간은 믿을 만한 위치가 20초 넘게 끊긴 상태에서 예상 종료 시각이 지나면 다음 구간으로 넘긴다. 예상 시각은 계획 시각에
  밀린 시간(`shift`)을 더한 값이다: 구간에 자동으로 늦게 들어왔으면(승강장 도착) `next_departures` 중 처음 탈 수 있는
  차까지, 사용자가 이전·다음 구간 버튼으로 옮겼으면 이미 타고 있다고 보고 가장 최근에 떠난 차까지, 그 값을 모르면 늦은
  만큼 민다(2026-09-18 사용자 결정). 손으로 되돌린 구간의 예상 종료가 이미 지났으면 늦은 만큼 밀어, 시간표 인계가 그
  구간을 곧바로 다시 넘기지 않게 한다. 위치 표본이 아예 끊기는 경우를 위해 화면이 10초마다 같은 판정을 돌린다. 남은
  도착 예정도 같은 `shift` 를 쓴다(남은 정거장 수는 여기에 위치로 읽은 지연을 더해 센다 — 아래 「늦은 열차에서도
  정거장 수가 맞게」). 버스 구간도 같은 규칙을 쓴다(2026-09-18 사용자 결정) — 버스는 지상이라
  평소에는 위치 판정이 먼저 서고, 위치가 20초 넘게 끊겼을 때만 시간표로 넘어간다.
- **단계·정차 추적**: `step_tracker.dart`(모퉁이 15m·선분 20/40m, 정확도 50m 초과 표본은 무시 — 단계는 앞으로만 가서
  한 번 잘못 넘기면 그 구간 내내 어긋난다), `stop_tracker.dart`(지상은 경로선 진행, 지하는 시간표 `offset_sec`, 값은 단조
  감소 — 시간표는 위치로 읽은 지연만큼 민다. 아래 「늦은 열차에서도 정거장 수가 맞게」).
- **문구**(`instruction.dart`): 화면 문구는 실시간 남은 거리·정거장 수를 넣는다. 음성은 문장이 아니라 안내 시점
  (`cueKey`: 탑승·하차 한 정거장 전·몇 번째 회전)마다 한 번만 읽는다(`voice_guide.dart`) — 처음에는 문장이 같을 때만
  건너뛰었는데, 탑승 문장에 남은 정거장 수가 들어 있어 역마다 다시 읽혔다(이슈 #73). 이어지는 `CONTINUE` 단계는 다음 실제
  회전까지 한 안내로 합치고, 출입구·엘리베이터처럼 그 자리에서 하는 동작은 문장 앞에 붙인다("역삼 1번 출구로 나가서 …").
  하차 뒤 "출구로 나가기" 는 다음 도보에 역 출입구가 있을 때만 쓰고, 버스에서 내린 뒤에는 다음 목적지를 안내한다.
- **알림창**(`status_notification.dart` ↔ `GuideStatusNotification.kt`): 위치 포그라운드 서비스의 "안내 중" 알림은 문구를
  바꿀 수 없어, 안내 전용 알림을 따로 띄워 "남은 N분 · 지금 할 일" / "도착 예정 HH:MM · 다음: …" 을 내용이 바뀔 때마다
  갱신한다(소리·진동 없는 채널, 안내가 끝나면 지운다). 화면 `docs/app/24-guide-notification.png`.
- **음성**(`tts_speaker.dart`): flutter_tts 4.2.5. 구글 엔진이 있으면 그걸 고르고(삼성 TTS 는 2025-06 부터 다른 앱에서 쓸 수
  없다), `setAudioAttributesForNavigation()` + `speak(focus: true)` 로 음악·영상 소리를 잠깐 줄인다. 설정 화면의 "음성 안내"
  스위치로 끈다. 엔진이 없으면 상태줄에 "음성 엔진 없음" 을 띄우고 소리 없이 진행한다.
- **지도**: 매 위치마다 따라가고(줌 17 이상 유지), 손으로 지도를 옮기면 따라가기를 멈추고 오른쪽 아래에 재중심 버튼이
  나온다(`docs/app/21-guide-recenter.png`).
- **궤적**: 샘플에 `activity_raw`·`activity_conf`(활동 인식 원시 판정·신뢰도)를 같이 올린다. 끈적 판정 전 값이라 "판정이 안
  왔다" 와 "직전 값이 유지됐다" 를 사후에 구분할 수 있다. 속도 계산은 그대로 `activity` 만 쓴다(마이그레이션 `0004`).

## 늦은 열차에서도 정거장 수가 맞게 (이슈 #85)

계획한 차를 놓치고 다음 차를 타면 남은 정거장 수가 계획 시간표대로 줄어 하차 안내가 몇 정거장 먼저 나갔다. 구간에
들어올 때 한 번 재는 `LegTracker.shift` 가 0 이었기 때문이다 — 승강장에 닿기 전 환승 통로에서 구간이 넘어가면 계획
출발보다 이른 시각이라 밀린 시간이 잡히지 않는다.

`stop_tracker.dart` 는 위치를 볼 때마다 그 지점을 **계획 시간표 위의 한 점으로 바꿔**(경로선 진행 거리로 정차 사이를
비례 배분) 계획 시각과 견주고, 그 차이를 지연(`_delay`)으로 삼는다. 시간표 판정은 정차 시각을 그만큼 민다.

- 승강장에 서 있으면 진행이 0 이라 **기다린 시간이 그대로 지연으로 잡힌다** — 이번 결함의 핵심이다.
- 정차 사이를 계획대로 달리는 동안에는 지연이 0 이다. 직전 정차 시각과만 견주면 정상 주행 시간이 지연으로 쌓여 남은
  정거장 수가 한 정거장 늦게 줄어든다.
- 늦은 쪽으로만 고친다. 계획보다 이른 열차는 위치 판정이 알아서 세고, 시간표를 당기면 하차 안내가 되레 일찍 나간다.
- **위치로 확인한** 통과 정차보다 앞으로는 되돌리지 않는다. 뒤로 크게 튄 표본을 "지금 여기" 로 읽으면 지연이 크게 잡혀
  굳고, 이번에는 하차 안내가 되레 늦게 나간다. 바닥으로 쓰지 않기로 한 값이 둘 있다.
  - "지금까지 가장 먼 지점" 은 쓰지 않는다. 실기기 궤적에서 환승 통로를 걷는 동안 투영이 앞쪽으로 튀었는데, 그것을
    기준으로 삼으면 그 뒤 승강장 대기 15분을 한 번도 읽지 못했다. 통과 정차 수는 정차 단위로만 움직이므로 정거장
    간격만큼 튀어야 기준이 옮겨진다.
  - 화면에 쓰는 남은 정거장 수도 쓰지 않는다. 거기에는 시간표로 줄어든 값이 섞여 있어, 위치가 잠깐 끊긴 사이 시간표가
    한 정거장 줄여 놓으면 돌아온 정상 표본이 "이미 지난 정차" 로 걸러진다.
  - 같은 정차 구간 안에서 뒤로 튀는 것은 걸러지지 않아 지연이 그 구간 주행 시간만큼 커질 수 있다.
- 중간 정차 앞뒤 30m 안에서도 재지 않는다. `offsetSec` 은 **도착** 시각이고 출발 시각은 받아오지 않아(`client.go` 의
  `intermediatePlaces { arrival }`), 계획대로 서 있는 시간이 지연으로 잡힌다. 그 시간은 지하철 시각표 기준 20~30초다
  (`gtfs/internal/build/metro.go` 가 시각표의 도착·출발을 그대로 쓴다). 버스는 생성기가 정차 시간을 주행 시간에 섞어
  도착·출발을 같게 쓰므로 해당되지 않는다. 대가로 두 가지가 남는다 — 중간 정차에서 오래 붙잡혀 있는 지연은 그 역을
  30m 벗어나기 전에는 읽지 못하고, 역을 벗어난 뒤 30m 지점에서 처음 재는 값에는 그 정차 시간이 섞여 들어온다(거리로
  나눠 배분하므로 30초를 조금 넘을 수 있다). 둘 다 출발 시각을 받아와야 없어진다. 방향은 안내가 조금 늦어지는 쪽이다.
- 위치를 한 번도 못 본 구간은 지연이 0 이라 계획 시간표 그대로다. 정시 열차가 승강장 표본 하나만 남기고 지하로 들어가는
  흔한 경우가 여기 해당한다 — 남은 정거장 수가 그대로 줄어 하차 안내가 나간다(회귀 테스트로 고정).

**검증** — 계획보다 약 10분 늦은 차를 탄 실기기 궤적 1건(지상 노선, 중간 정차 11곳, 표본 628개)을 두 코드에 그대로
재생했다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| "다음 역에서 내리세요" 시점 | 하차역 네 정거장 전 | 하차역 한 정거장 전 |
| 시간표로 떨어진 뒤 굳은 값 | 남은 5(위치 판정은 9) | 없음 — 위치 판정 그대로 줄어듦 |

단위 테스트 9개를 더했고, 그중 5개는 고치기 전 코드에서 실패한다. 아홉 개가 함께 막는 것은 이 결함을 고치는 길에 놓인
함정들이다 — 시간표를 억누르면 하차 안내가 아예 안 나가고, 직전 정차 시각과만 견주거나 정차 앞뒤 표본을 재면 정상
주행·정차 시간이 지연으로 쌓이고, 뒤로 튄 표본을 재면 안내가 되레 늦어지고, 지연을 줄이는 쪽으로도 고치면 안내가 일찍
나간다. 뒤로 튄 표본을 "지금까지 가장 먼 지점" 이나 화면용 남은 정거장 수로 막으면 승강장에서 기다린 시간을 못 읽는다.
모두 Codex 교차 검토에서 나왔다.

## 알려진 한계

- 도착 예정 시각은 구간에 들어온 시각과 탄 차를 기준으로 밀린 만큼(`LegTracker.shift`)만 늦춘다. 한 구간 안에서 지체한
  시간은 다음 구간에 들어갈 때까지 반영되지 않아 그동안은 낙관적이다.
- 구간 넘김은 구간에 들어온 시각으로 한 번 잰 `shift` 를 쓰므로, 그 뒤로 더 늦어지면 환승 안내가 그만큼 이르다. 되돌리는
  판정은 없어 그때는 이전 구간 버튼으로 맞춘다. 남은 정거장 수만 위치로 읽은 지연을 반영하고(#85), 도착 예정 시각은
  아직 `shift` 를 쓴다.
- 경로를 벗어나도 재탐색하지 않는다(#67 범위 밖). 구간 표시가 실제와 어긋나면 사용자가 이전·다음 구간 버튼으로 맞춘다.
- 구간 넘김·단계 전환 상수(25/40/60m, 15/20/40m, 정확도 상한 50m)와 위치 2초는 초기값이고 실기기 궤적으로 재보정하지
  않았다.
- 응답이 2배로 커졌다(서울역→강남역 35KB). 후보 수를 늘리면 더 커진다.
